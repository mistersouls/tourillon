## Summary

This proposal introduces a daemon-internal garbage collection (GC) engine that runs as a
background `asyncio.Task` on a configurable interval. The engine evicts confirmed
tombstones, expires unreplayed hints, and cancels stale rebalance staging entries.
A `tourctl gc status <addr>` command gives operators a live view of pending work and the
last GC run timestamp. All configuration lives in a new `[gc]` section in `config.toml`.
The GC engine is self-contained: it never modifies the ring, gossip state, or
`NodeState`; it acts only on stored records accessed through the `BackendStorage` port.
The GC task is started and cancelled by the same `Bootstraper` / `TourillonCore`
composition root introduced in proposal 001, so its lifecycle remains aligned with the
peer and KV listeners instead of being managed by a separate ad hoc startup path.

---

## Motivation

Without explicit reclamation, three categories of storage waste accumulate indefinitely:

1. **Tombstones** — deletion markers that have been acknowledged by a write-quorum are
   still needed until every replica has incorporated them, but after that point they
   consume space forever if not evicted.
2. **Hints** — hinted-handoff records are written when a replica is temporarily
   unavailable and replayed once it recovers. Successfully replayed hints are never
   deleted by the write path; unreplayed hints from permanently dead nodes also linger.
3. **Stale staging entries** — a rebalance transfer that stalls in `PENDING` with no
   chunk progress occupies staging space and holds a transfer handle open, preventing
   the partition from being cleanly reclaimed.

Without GC, storage nodes grow without bound; diagnostics for why are opaque to
operators. This proposal addresses all three waste categories with a single, observable
background task.

## CLI contract

### GC status

```
$ tourctl gc status 10.0.0.3:7100
GC status for 10.0.0.3:7100
  Last run:               2026-05-31T14:02:07Z (42s ago)
  Tombstones pending:     12
  Hints pending:          3
  Stale staging entries:  0
```

With `--json`:

```json
{
  "last_run_ts": "2026-05-31T14:02:07Z",
  "last_run_ago_s": 42,
  "tombstones_pending": 12,
  "hints_pending": 3,
  "stale_staging": 0
}
```

When GC has never run (daemon just started):

```
$ tourctl gc status 10.0.0.3:7100
GC status for 10.0.0.3:7100
  Last run:               never
  Tombstones pending:     0
  Hints pending:          0
  Stale staging entries:  0
```

### Errors

```
# Connection failure
$ tourctl gc status 10.0.0.3:7100
Error: connection failed: <reason>
```

All errors are written to **stderr**; exit code is **1** on error, **0** on success.

## Design

### Configuration

A new `[gc]` section is added to `config.toml`. All duration fields use
unit-embedded strings:

```toml
[gc]
interval          = "300s"   # how often the GC task fires
tombstone_min_age = "1h"     # minimum age before a confirmed tombstone is evicted
hint_ttl          = "24h"    # max age for an unreplayed hint
staging_ttl       = "1h"     # max idle time before a stale PENDING transfer is cancelled
```

Accepted duration suffixes: `ms`, `s`, `m`, `h`. An unrecognised suffix is a fatal
config error at startup. Fields default to the values shown above when the `[gc]`
section is absent.

The config loader parses duration strings via the shared helper
`parse_duration(s: str) -> float` (seconds, defined in `bootstrap/config.py`). The
parsed float values are carried by a `GcConfig` dataclass:

```python
@dataclass(frozen=True)
class GcConfig:
    interval_s: float = 300.0
    tombstone_min_age_s: float = 3600.0
    hint_ttl_s: float = 86400.0
    staging_ttl_s: float = 3600.0
```

### GC engine

The engine lives in `tourillon/core/gc/engine.py`. It is started during daemon bootstrap
as a long-lived `asyncio.Task` and cancelled on shutdown:

```python
class GcEngine:
    async def run(self) -> None:
        """Loop: sleep interval_s, then sweep. Cancelled cleanly on shutdown."""
        ...
    async def sweep(self) -> GcSweepResult:
        """One full pass over all three waste categories."""
        ...
    def last_result(self) -> GcSweepResult | None:
        """Return the result of the most recent sweep, or None if never run."""
        ...
```

`GcSweepResult` is a frozen dataclass carrying the counts and timestamp:

```python
@dataclass(frozen=True)
class GcSweepResult:
    swept_at: datetime          # UTC timestamp of sweep completion
    tombstones_evicted: int
    hints_expired: int
    staging_cancelled: int
    tombstones_pending: int     # count of tombstones still within min_age
    hints_pending: int          # count of hints not yet replayed
    stale_staging: int          # count of stale PENDING transfers found
```

The engine holds a reference to `Storage` (from `core/ports/storage.py`) and the
`GcConfig`. It never touches `NodeState`, the ring, or gossip.

### Tombstone eviction

A `Tombstone` (from `core/structure/record.py`) is eligible for eviction when **both**
conditions hold:

1. **Quorum-confirmed**: `tombstone.quorum_write` replicas have acknowledged the delete.
   The GC engine reads `Value.quorum_write` from the stored `TaggedRecord` and compares
   it against the cluster's configured `quorum_write` (W). A tombstone written with
   `quorum_write >= W` is confirmed.
2. **Old enough**: the tombstone's HLC wall-clock component is older than `now -
   tombstone_min_age_s`. The GC engine uses `time.time()` as the wall-clock reference.

**Walk**: `BackendStorage.iter(Namespace.TAGS, ...)` over the `namespace_tags` namespace,
filtering for entries whose `Tag.kind == TagKind.TOMBSTONE`. For each eligible tombstone,
call `BackendStorage.delete(tagged_record)` to remove it from both `namespace_log` and
`namespace_tags`.

Non-eligible tombstones (not yet confirmed, or within min-age) are counted as
`tombstones_pending` in the result.

### Hint expiry

Hints are stored with `Tag.kind == TagKind.HINT`. A hint is eligible for deletion when
**either** condition holds:

1. **Successfully replayed**: the hint's corresponding `TaggedRecord` has
   `tag.kind == TagKind.LIVE` or `TagKind.TOMBSTONE` in the same partition (the replay
   write promoted it). The GC engine detects this by looking up the hint's `Address` in
   `Namespace.LOG`: if a non-HINT entry exists with the same or newer HLC, the hint has
   been superseded.
2. **TTL expired**: the hint's HLC wall-clock component is older than `now - hint_ttl_s`.

**Walk**: `BackendStorage.iter(Namespace.TAGS, ...)`, filtering for `TagKind.HINT`.
For each eligible hint, call `BackendStorage.delete(tagged_record)`.

Non-eligible hints are counted as `hints_pending`.

### Stale staging cleanup

A staging entry has `Tag.kind == TagKind.STAGING`. A staging context is stale when it is
in `PENDING` state with no chunk progress for longer than `staging_ttl_s`. The GC engine
uses the HLC timestamp of the most recent staging entry for a given `(pid, epoch)` as the
last-activity marker.

**Walk**: `BackendStorage.iter(Namespace.TAGS, ...)`, filtering for `TagKind.STAGING`,
grouping by `(pid, epoch)` (encoded in the `Tag.payload`). For each group whose
most-recent timestamp is older than `now - staging_ttl_s`:

1. Mark the transfer as `CANCELLED` in the staging index (if one exists).
2. Delete all staging entries for the group via `BackendStorage.delete(...)`.

Cancelled staging entries are counted as `staging_cancelled`; still-active-but-pending
entries are counted as `stale_staging` (i.e. they were identified as candidates but are
within TTL).

### `gc.status` handler

The handler lives in `tourillon/core/gc/handlers.py`:

```python
@dispatcher.on("gc.status")
async def handle_gc_status(receive, send) -> None:
    """Return current GC counts and last run timestamp."""
    ...
```

The handler reads from the `GcEngine.last_result()` snapshot (no lock needed; the
snapshot is replaced atomically as a single reference assignment). It builds a
`gc.status.response` envelope and sends it. If the engine has never run, all counts are
`0` and `last_run_ts` is absent from the payload.

A `register(dispatcher, engine)` module-level function wires up the handler with the
live `GcEngine` instance.

### Envelope kinds

| Kind | Direction | Payload fields |
|---|---|---|
| `gc.status` | tourctl → peer | *(empty)* |
| `gc.status.response` | peer → tourctl | `last_run_ts: str \| None`, `tombstones_pending: int`, `hints_pending: int`, `stale_staging: int` |

Both envelope kinds travel on the **peer plane** (mTLS peer listener).

### Concurrency and safety

- The GC engine runs as a single `asyncio.Task`; no concurrent sweeps are possible.
- `BackendStorage` calls are awaited sequentially within a sweep. No batch-delete
  transaction is assumed; each `delete()` call is atomic at the record level.
- The engine does not hold any application-level lock during a sweep. If a write
  arrives for a key being deleted, the write wins (its HLC is newer). This is safe
  because GC only deletes records that are logically superseded (confirmed tombstones,
  replayed hints) or administratively cancelled (stale staging).
- A sweep that is interrupted by a shutdown `CancelledError` leaves storage in a
  consistent state: each `delete()` is individually atomic, so a partial sweep merely
  defers some evictions to the next run.

```
tourillon/core/gc/
```

### Error paths

| Condition | Behaviour |
|---|---|
| `BackendStorage.delete()` raises `OSError` | Log warning; count the record as not evicted; continue sweep |
| `BackendStorage.iter()` raises mid-walk | Log error; abort sweep; do not update `last_result`; retry at next interval |
| `gc.status` received before first sweep | Respond with all-zero counts and absent `last_run_ts` |
| Transport / mTLS error in `tourctl gc status` | Print `Error: connection failed: <reason>` to stderr; exit 1 |
| Unknown duration suffix in `[gc]` config | Raise `ConfigError` at startup with message `"unknown duration suffix '<suffix>' in gc.<field>"` |

## Design decisions

### Decision: Background task (option A) over explicit trigger

**Alternatives considered:** (B) Event-driven GC triggered by write-quorum acknowledgement;
(C) On-demand only via `tourctl gc run`.

**Chosen because:** A periodic background task is operationally simple, predictable, and
observable via `gc.status`. Option B requires instrumenting every write path and is
significantly more complex. Option C provides no reclamation without operator action.
A future `tourctl gc run` command can trigger an immediate sweep without replacing the
periodic model.

### Decision: Counts-only `gc.status` (no enumeration of pending records)

**Alternatives considered:** Return a list of pending tombstone addresses in the response.

**Chosen because:** Enumerating large datasets in a single response is unsafe (unbounded
payload). Counts are sufficient for dashboard monitoring and alerting. Operators who need
the full list can use storage-level tooling.

### Decision: HLC wall-clock component for age comparison

**Alternatives considered:** A separate `created_at` field attached to every record.

**Chosen because:** The HLC timestamp's wall-clock high bits already encode the physical
time of the write. Using the HLC avoids adding a new field to `KvMetadata` or `Tombstone`.
Clock skew tolerance is inherited from HLC semantics (wall-clock drift is bounded to the
HLC's epsilon window, which is already assumed safe for causal ordering).

### Decision: GC does not modify `NodeState` or ring

**Chosen because:** GC is a storage-layer concern. Separating it from lifecycle state
prevents accidental topology mutations during maintenance sweeps and keeps the GC engine
independently testable.

## Interfaces (informative)

```python
# tourillon/core/gc/engine.py
from __future__ import annotations

import asyncio
import time
from dataclasses import dataclass
from datetime import datetime, timezone
from typing import TYPE_CHECKING

if TYPE_CHECKING:
    from tourillon.core.ports.storage import BackendStorage

from tourillon.core.structure.machinery import Namespace, TagKind


@dataclass(frozen=True)
class GcConfig:
    interval_s: float = 300.0
    tombstone_min_age_s: float = 3600.0
    hint_ttl_s: float = 86400.0
    staging_ttl_s: float = 3600.0


@dataclass(frozen=True)
class GcSweepResult:
    swept_at: datetime
    tombstones_evicted: int
    hints_expired: int
    staging_cancelled: int
    tombstones_pending: int
    hints_pending: int
    stale_staging: int


class GcEngine:
    def __init__(self, backend: BackendStorage, config: GcConfig) -> None:
        self._backend = backend
        self._config = config
        self._last_result: GcSweepResult | None = None

    async def run(self) -> None:
        while True:
            await asyncio.sleep(self._config.interval_s)
            result = await self.sweep()
            self._last_result = result

    async def sweep(self) -> GcSweepResult:
        ...

    def last_result(self) -> GcSweepResult | None:
        return self._last_result


# tourillon/core/gc/handlers.py
from tourillon.core.transport.dispatcher import Dispatcher
from tourillon.core.gc.engine import GcEngine


async def handle_gc_status(receive, send) -> None:
    """Handle gc.status envelope; respond with counts and last run timestamp."""
    ...


def register(dispatcher: Dispatcher, engine: GcEngine) -> None:
    dispatcher.on("gc.status")(
        lambda receive, send: handle_gc_status(receive, send)
    )
```

## Out of scope

- `tourctl gc run` on-demand trigger (may be added in a later revision).
- Per-partition GC parallelism (single-threaded sequential sweep is sufficient for the
  initial implementation).
- GC metrics export (Prometheus / OpenTelemetry integration is a separate proposal).
- Compaction of the underlying storage engine (engine-level compaction is an infra
  adapter concern, not a domain concern).
- Automatic GC triggering from write-quorum acknowledgements (option B considered and
  deferred; see design decisions above).
- `[gc]` configuration hot-reload without daemon restart.
